## 3. Decision table (review-guidelines §"decision table")

| Identity / case | Namespace and uniqueness | Who may set or change it | Frozen vs live | Result / priority |
| --- | --- | --- | --- | --- |
| Account email | Normalised (trim, lower-case domain, NFC); unique per subject, globally unique (D6) | Set by the inviting admin; changed only by a two-person admin change, which revokes all sessions | Live; audit keeps the history | Proof of control is a code sent to it. **It never authorises anything by itself** |
| Google identity | `(iss = https://accounts.google.com, sub)` | The account holder links it from a session that already passed MFA, or while accepting an invitation (WP4: for an address Google manages — see WP4 decisions) | Live; unlink audited; **revoked by an approved MFA reset or a completed email change** (0123) | Matched only by `(iss, sub)`. Email in the token is display-only |
| Microsoft identity | `(tid, oid)` from a v2.0 ID token; issuer must equal `https://login.microsoftonline.com/{tid}/v2.0` for that token's `tid` | Same as Google | Live; revoked by recovery like Google (0123) | Matched only by `(tid, oid)`. `email`, `preferred_username` and `upn` are never used for matching (Microsoft: these values are mutable and must not be used for authorization; identify users by `oid` / `sub`) |
| Passkey | WebAuthn credential ID, RP ID = web host | Holder enrols from a session at the required level; admin can only revoke | Live; sign counter tracked | Phishing-resistant factor |
| TOTP secret | One per subject | Holder enrols; admin can only revoke | Live | Second factor, not phishing-resistant |
| Recovery codes | 10 single-use, hashed | Generated at MFA enrolment; regenerating voids the old set | Each code frozen once used | Restores the second factor only; forces re-enrolment and revokes all sessions |
| Invitation | Random token, hashed; one email, one tenant, one organisation | Created by an admin action; **roles are not in the invitation** — they are requested through the existing two-person role-grant flow | Single use, expires in 72 h, revocable | Accepting creates the subject. Without a role binding the account sees "access pending" and no private data |
| Session | Opaque token, hashed; keyed by `subject_id`, carries tenant, first-factor method, second-factor method and time | Issued only by the login flow; revoked by logout, admin, recovery, email change, authenticator removal or unlinking the identity it rests on | Live, re-checked every request | Authentication level (AAL) is derived from what the session proved, **never declared by an admin** |
| Identity assurance (`assurance_level`) | Per subject (moves from the wallet row) | Admin with justification, as today | Live | Separate dimension from AAL. A role needs **both** its identity-assurance minimum and its AAL minimum |
| Signing wallet | `(wallet_address, chain_id)`, unique; bound to one subject | Holder binds it by signing a binding message from an MFA session (proof of possession). Admin can only disable | Live; `bound_at`, `disabled_at` | Required for attestation and gate-decision signatures; never a login |
| Service token | Hashed token bound to a `service` subject, route-scoped | CLI only | Expires; rotation overlaps | Cannot reach any person-only route; no MFA concept |
| Historical audit rows | `actor_wallet` stays as written | Nobody (append-only) | Frozen | New rows record `actor_subject_id` and, for signed actions only, the signing wallet |

**Priority of overlapping conditions** (evaluated in this order, first match wins):

1. Revoked or expired session, disabled subject, revoked authenticator used by the session → 401.
2. Session below AAL2 (first factor only) → only MFA enrolment, MFA challenge and logout.
3. No role binding → "access pending"; public reads only.
4. Role binding present but session AAL or identity assurance below the role minimum → that role is not effective for this request (same narrowing rule as today: narrowed, never widened).
5. Otherwise the existing authorisation rules apply unchanged.

### WP3 decisions (second factor)

Taken while implementing WP3 (migrations 0115–0117, `apps/api/src/routes/mfa.ts`) and its security
review (0118); each is
enforced in the database functions, and the API only verifies cryptography.

| Case | Decision | Why |
| --- | --- | --- |
| Where a factor comes from | `core.create_subject_session` refuses a second factor. A session is raised only by a function that consumes its evidence (a WebAuthn challenge this session asked for, a TOTP step, an unused recovery code) and writes a proof row; a CHECK and a composite foreign key `(proof, session, factor)` refuse a factor without its own proof, even to the table owner | AAL is derived from what was proved (§3), so the column must not be writable on its own |
| First enrolment from an aal1 session | Only while the subject holds no passkey or TOTP, and only within 24 h of the subject's creation (invitation acceptance) or of an approved admin reset | Otherwise whoever holds the first factor (a mailbox, an IdP account) could add their own authenticator |
| Adding a factor later | aal2; a passkey when one already exists needs aal3 | A TOTP session must not mint a passkey and so reach passkey-only roles |
| Removing a factor | Needs the level of the strongest factor held, the one removed included (aal3 while any passkey exists); never the last factor; ends every other session, and this one if it rested on the removed factor | A TOTP session must not strip a passkey; a lost-everything account goes through the admin reset |
| Sign counter | Accepted if both the stored and the new counter are 0 (authenticators that never count, such as synced passkeys), otherwise only if the new one is strictly greater. Checked under the credential's row lock | Stricter than "accept 0": once a credential has counted, a 0 is a regression (clone) |
| TOTP | SHA-1, 6 digits, 30 s, ±1 step; the accepted step is recorded and a step at or before it is refused on any session; 5 attempts per 15 min per authenticator, counted (and committed) **before** the code is checked, reset by a success | Counting first means an abandoned or failed request still counts |
| TOTP secret at rest | AES-256-GCM, key from `SESSION_SECRET` via HKDF-SHA256 `mpc/totp-secret/v1` (D10), AAD binds the row id and subject. Rotating `SESSION_SECRET` makes every TOTP unreadable (`MFA_TOTP_UNREADABLE`); holders use a passkey or a recovery code and re-enrol | No second key to manage for the MVP; the rotation cost is documented in deployment |
| Recovery codes | 10 × 16 base32 characters (80 bits), plain SHA-256 (D10: a random token needs no key), single use; generated with the first factor; regenerated (voiding the old set) only from a session at the level of the strongest factor held (aal3 while a passkey exists), never from a recovering session | A recovering session may enrol a passkey, so a fresh code set is worth a passkey: a TOTP session that could mint codes could mint itself a passkey (found in WP3 security review) |
| Using a recovery code | Only from an aal1 session. Every other session of the subject ends at once; the recovering session is limited to MFA enrolment and logout. Proving a factor from it (enrolling a new one, or a found passkey / TOTP) completes the recovery and ends every session, that one included, and the person signs in again (journey 5) | The recovering session is the only way left to enrol, so it ends after the enrolment, not before |
| Admin MFA reset (journey 6) | Two people with `mpc_operator` or `security_operator` at aal3; the decider is not the proposer and neither decides their own reset; approval revokes every passkey and TOTP, voids the recovery codes, revokes every linked Google / Microsoft identity (0123), ends every session, and opens a 24 h first-enrolment window. It never adds an authenticator | An admin must never be able to attach a factor to someone else (AUTH-09) |
| Recovery separation (security review, 0118) | Whoever proposed or decided an email change of a person (pending, approved or completed, within 30 days) can neither propose nor approve an MFA reset of that person; whoever proposed or decided a pending or approved reset (within 30 days) can neither propose nor approve an email change of that person. Rejections are always allowed. Enforced in the database, answered as `ACCOUNT_RECOVERY_SEPARATION_REQUIRED` | Each flow is two-person, but the same two admins could move the address to a mailbox they read and then reset the factors — a takeover. Counting changes from proposal, not only completion, stops "approve the change, reset, then complete" |
| Reset notice (0118) | Approval queues `mfa_reset_notice` (no code, no link, "if this wasn't you, contact your administrator") to the current address and to every address the account was moved away from within **90** days (0119); the completed change keeps that previous address for those 90 days, unreadable by the application role, then the purge clears it | The owner a chain would lock out still reads the old address. 90 rather than 30 days: with both at 30, the same pair could reset one minute after the separation lapsed and only the new (attacker's) address would be told |
| Email change without an address (0118) | Refused (`EMAIL_CHANGE_NO_ADDRESS`). Eligible legacy operators retain their historical subject through explicit migration-only `BOOTSTRAP_SUBJECT_ID` cutover; it initializes a NULL email with no account/provider/MFA/recovery history and requires existing active role and adequate stored assurance. Other legacy people migrate by invitation as new subjects, with two-person role grants; new people use invitations | Ordinary admins cannot attach an email (§5); the narrow cutover trusts an authorized deploy operator's explicit UUID mapping and never grants authority |
| Bootstrap enrolment window (0118) | Ordinary email bootstrap can reopen a 24 h first-enrolment window for an existing person who holds no passkey or TOTP, recorded as a `bootstrap` reset row and audited as `deploy_bound`; it opens nothing once a factor exists. Explicit legacy cutover opens a bootstrap window with the initial email assignment only when the creation-time window has expired; a same-subject/email rerun is a no-op | The first operator past their first 24 hours has no second admin to approve a reset |
| Lock order (0118) | Subject row before session rows, in every MFA function and in session revocation; a deadlock or serialization abort answers 409 `CONCURRENT_REQUEST`, retryable | Two MFA calls of one person from two sessions (the same recovery code twice) deadlocked |
| Subject creation time (0118) | Not writable by the application role; a CHECK refuses a creation more than five minutes ahead | The 24 h first-enrolment window runs from it |
| WebAuthn relying party | `WEBAUTHN_RP_ID` and `WEBAUTHN_ORIGIN` are required in production; the origin is a bare `https` origin on the RP ID or a subdomain, and equals the web origin invitation links point at (`WEB_ORIGIN`, WP2); user verification required; attestation `none` | |

### WP4 decisions (Google / Microsoft)

Taken while implementing WP4 (migrations 0120–0121, `apps/api/src/routes/oidc.ts`,
`apps/api/src/services/oidc.ts`). Who may start, claim and complete a flow is decided in the
database functions; the API does the code exchange and ID-token validation (`openid-client`).

| Case | Decision | Why |
| --- | --- | --- |
| Library and flow | `openid-client` 6 (pinned), authorization code + PKCE S256, `state`, `nonce`, `prompt=select_account`; the ID token's signature is verified against the provider's published keys (`enableNonRepudiationChecks`) and `azp`, when present, must be our client id | The library by default trusts TLS for a token-endpoint ID token and compares `azp` only with several audiences; both checks are cheap and the token is the only evidence of who signed in |
| Redirect URI | `<WEB_ORIGIN>/auth/oidc/{google,microsoft}/callback` on the web app. `OIDC_REDIRECT_BASE` exists only to say it explicitly and must equal `WEB_ORIGIN` (https in production). The callback page posts `code` and `state` to the API | One origin for the browser, the same as invitation links and passkeys; nothing for an attacker to point elsewhere |
| Microsoft endpoint | `https://login.microsoftonline.com/organizations/v2.0` (work and school accounts); the personal-account directory `9188040d-…` is refused. `iss` must equal `https://login.microsoftonline.com/{tid}/v2.0` for the token's own `tid` (library and again in our code); `MICROSOFT_ALLOWED_TENANTS` (GUIDs) restricts the directories, unset allows any directory | Personal accounts are out of scope for a business registry; `common` would admit them |
| Keys | Google `(https://accounts.google.com, sub)`; Microsoft `(issuer naming tid, oid)` — the same `oid` in another directory is another identity. One live identity per `(provider, issuer, key)` across all tenants and one per provider per account | §3: never email, `preferred_username` or `upn` |
| Login CSRF | `start` returns a `browserBinding` with the authorization URL; the database keeps only its SHA-256 and the callback must present it with `state`. A wrong binding (or provider, or session) refuses without spending the flow; an expired one spends it | The plan's cookie (§5) is the web's job (WP6): it keeps the binding in an HttpOnly cookie or session storage of the tab that started; the API checks it either way |
| Flow record | `core.oidc_login_transactions`: hashes of state, binding and nonce; PKCE verifier and nonce sealed with AES-256-GCM under HKDF `mpc/oidc-tx/v1` (D10, AAD = transaction id), deleted at the claim; 10 min lifetime; claimed once; purged after a day by the jobs worker | A database dump leaks no usable flow |
| Session | A `google` / `microsoft` session exists only through a transaction this same database transaction completed for that subject (CHECK + trigger); `core.create_subject_session` refuses every first factor and is no longer the application role's. aal1, so MFA_REQUIRED everywhere else | Same pattern as the email-code session (WP2) |
| Sign-in | Only for a linked, live identity; unknown keys answer `OIDC_ACCOUNT_NOT_FOUND` whatever the email | §5 nOAuth |
| Linking | `/link/start` and `/link/callback` need an aal2, non-recovering session, the same one at both ends; an identity linked anywhere (this account, another, another tenant) answers one code, `OIDC_IDENTITY_UNAVAILABLE`; a second identity of the same provider `OIDC_PROVIDER_ALREADY_LINKED` | Linking adds a way in: same bar as adding a factor |
| Unlinking | aal2, non-recovering; never the last way in (no address and no other identity → `OIDC_LAST_SIGN_IN_METHOD`); ends every session the identity signed in, this one included | |
| Invitation with a provider | Accepted when the provider vouches for the invited address *now*: Google `email_verified` **and** the address is Gmail (`@gmail.com`, `@googlemail.com`) or in the Workspace domain the token's `hd` names exactly; Microsoft `xms_edov` (optional claim, must be configured on the app registration). A Google-verified address Google does not manage answers `OIDC_EMAIL_CODE_REQUIRED` (security review L7: a consumer Google account's `email_verified` dates from its sign-up and survives the address changing hands); otherwise `OIDC_EMAIL_NOT_VERIFIED` / `OIDC_EMAIL_MISMATCH`. The invitation stays usable with the emailed code in every refusal. Creates the subject (no role, `wallet_only`), links the identity, retires the invitation's outstanding code | **Departs from §3 ("after the email code")** — the provider's verified address replaces the code as proof of control. Needs the coordinator's confirmation; the code path is unchanged |
| Errors | The provider's `error` / `error_description` and token-endpoint text are never echoed or stored; the client sees `OIDC_ACCESS_DENIED`, `OIDC_PROVIDER_ERROR`, `OIDC_TOKEN_INVALID`, `OIDC_PROVIDER_UNAVAILABLE` (503) | Attacker-influenced text |
| Recovery (security review M3, 0123) | An approved MFA reset and a completed email change revoke every live linked identity of the subject in the same transaction (`revoked_reason` `mfa_reset` / `email_change`); the reset and change notices name the removed providers (never an identifier) and ask for them to be linked again; the holder re-links from an aal2 session | A sign-in someone linked during brief aal2 access would otherwise survive recovery and reach the 24 h enrolment window first |
| Configuration | Each provider is on only with both its client id and secret (production refuses one without the other); the secrets are optional deployment secrets, not required at synth | Absent is a valid state |

## 4. User journeys affected

1. **Invitation → first sign-in.** Admin invites → email with link → code to the same address → (optional) link Google / Microsoft → enrol passkey or TOTP → receive recovery codes → "access pending" until a two-person role grant lands.
2. **Returning sign-in.** Email code, Google or Microsoft → second factor → workspace. Unknown or uninvited emails get the same "if this address has access, a code was sent" response.
3. **Signing.** Reviewer opens a signature request → connects the bound wallet → signs EIP-712 → server checks the signer is an active wallet bound to the assignee (fixing the multi-wallet bug below). A wallet that is not bound is refused before signing.
4. **Binding a wallet.** From settings, at the required AAL: connect wallet → sign binding message (tenant, subject, nonce, expiry) → bound. One wallet cannot be bound to two subjects.
5. **Lost second factor.** Recovery code → re-enrol → every session revoked, including this one (clarified 2026-11-02: the session that used the recovery code ends too, and the person signs in again with the new factor). As implemented (WP3): using the code ends every other session at once; the recovering session can then only enrol a factor and sign out; proving a factor from it ends every session, that one included.
6. **Lost everything / offboarding.** Two-person admin recovery or suspension → sessions, second factors **and linked Google / Microsoft identities** revoked (0123), history and signatures kept (AC-27). The notice names the providers to link again.
7. **Email change.** Two-person admin action → code to the new address → all sessions **and linked Google / Microsoft identities** revoked (0123); the old address is told which providers to link again. Only an existing address can be changed, and the two admins take no part in an MFA reset of that person for 30 days (0118).
8. **Services.** Scan-worker and CRE use service tokens; their behaviour is otherwise unchanged.
9. **Public Explorer.** Unchanged, no login.

## 5. Security risks and the controls planned

| Risk | Control | Test that proves it |
| --- | --- | --- |
| Code brute force | 8 random digits, 10-minute TTL, 5 attempts per code, per-email and per-IP limits, HMAC-hashed with a key derived from `SESSION_SECRET` (D10), single use, constant-time compare | API negative tests: 6th attempt refused, reused code refused, expired code refused, limit per email across IPs |
| Account enumeration | Identical response and timing for invited and uninvited addresses | Response-equality test |
| Account takeover via an identity provider (nOAuth-style email matching) | Link only by `(iss, sub)` / `(tid, oid)`, only from an authenticated flow; never by email | Test: a Microsoft token with a matching email but unknown `oid` does not sign in |
| OIDC flow attacks | Authorization code + PKCE, `state` and `nonce` bound to a short-lived HttpOnly cookie, exact redirect URI, issuer and audience checks, Microsoft per-`tid` issuer | Tests for wrong state, replayed code, wrong issuer, wrong audience, missing nonce |
| Session theft | Token moves from `localStorage` to an HttpOnly `__Host-` cookie on the web origin; the same-origin proxy forwards it to the API as today's bearer. Mutations require same-origin `Origin`. Absolute TTL 8 h, idle timeout 30 min | XSS-independent: cookie not readable by script (E2E); cross-origin POST refused |
| MFA bypass | AAL derived from the session's proven factors; priority rule 2 and 4 above | Tests: first-factor session cannot read restricted data; TOTP session cannot use a passkey-only role |
| Admin attaches their own login to someone else's account | Admins cannot add emails, identities or authenticators to another subject; only invitations (new subject) and two-person email change | Negative API tests for each |
| Recovery abuse | Recovery code restores only the second factor and revokes sessions; full recovery is two-person | Tests |
| Invitation token leak | Hashed, single use, 72 h, tied to the invited email (code still required) | Tests: reuse, expiry, different email |
| Wallet binding without possession | Signed binding message with nonce and expiry | Test: binding with a signature from another key refused |
| Multi-wallet signer ambiguity | Superseded by D11 (`0130`): one active wallet per account, so the signer must be the assignee's active wallet; a replace moves signing to the new key atomically | Replace tests: old key refused, earlier signatures stay attributed |
| Email and identity data handling | Stored minimal (email, provider ids, display name); excluded from public projections and exports; production gated on OD-17/18 | Projection/export allowlist tests |

The threats these controls answer are listed once, in [threat model T10](security/threat-model.md); §2 boundary 2 there changes from "holds a SIWE session" to "holds an account session".

WP5 as built (2026-11-02, migration `0122`), where it departs from the row above. **Revised by `0130` (2026-11-03, D11): one active wallet per account** — the items below marked *(0130)* replace what they contradict:

- *(0130)* **One active wallet, 1:1.** `(wallet_address, chain_id)` is unique among active rows only (it was unique over every row, so a disabled address could never be bound again), and `(subject_id)` is unique among active rows. Existing multi-wallet data (dev and seed only) was consolidated by the migration: the designated governance wallet if still active, else an operator-verified one before a proof binding, then the highest assurance, then the most recently bound one, is kept (review F4: the first revision kept the newest, which let a later dev-chain proof wallet displace the operator-verified key); the others are disabled with reason `consolidated_single_wallet` (no deciding person) and audited `migration.wallet.consolidated`; no session ended.
- *(0130)* **Replace is the bind ceremony.** With no wallet, a bind binds. With one, the challenge names it (`replaces`, and the human-readable text says "This replaces your current signing wallet 0x…"), the screen shows it before the wallet opens, and the bind disables the old wallet (reason `replaced`, decided by the person) and binds the new one in one transaction under the subject lock — never zero, never two. A challenge issued before the account's wallet changed is refused as stale (`WALLET_CHALLENGE_INVALID`); the active address again is `WALLET_ALREADY_ACTIVE`. The holder says why (`replaceReason`: `rotation` by default, `key_lost`, `key_compromised`), recorded on the disable event (`replace_cause`). Audit `account.wallet.replaced` with `oldWalletId` / `newWalletId` / `replaceReason` and the assurance before and after. Needs the strongest factor held, like every bind. **Assurance** follows the disable rule: replacing an operator-verified wallet (`bound_via = 'operator'`) lowers the identity assurance to `wallet_only` until an admin verifies the person again (the screen says so before signing); replacing a proof-bound wallet leaves it as it is.
- *(0130)* **Sessions.** A replace keeps every session: the old key stops signing in the same transaction and a wallet signs nobody in. A disable without replacement still ends every session of the person (AC-27) and leaves the account with no signing wallet.
- *(0130)* **Re-binding a disabled address** works for the same person and for a new holder, by the same proof ceremony; it inserts a new row, audited with `rebindOf` (the previous row, looked up in every tenant) and `rebindSameSubject`. **Never for a key ever disabled as compromised** (`key_compromised`, or a replace with that cause) **or disabled by an admin**: refused with the same `WALLET_UNAVAILABLE`, the same person included, the history read across tenants. **A lost key** (`key_lost`, or a replace with that cause), a wallet consolidated by `0130` and a disabled row with no recorded event **come back only to their own subject**; `rotation` and `offboarding` keys can be bound by anyone who proves them. Comparisons are NULL-safe and an unknown subject or decider refuses. The function runs with `row_security = off`, so an owner without `BYPASSRLS` fails loudly instead of checking one tenant — as, since `0131`, does every other definer function from `0112`–`0130` that reads across tenants (sign-in, invitations, email change, OIDC, purges, the vote pin) and the older session and service-token resolvers that read before a tenant is set (`resolve_session`, `revoke_session`, `resolve_service_token`, `resolve_role_bindings`); the audited list is in that migration's header. The deploy's `bootstrapCredential` refuses a wallet address with disabled history (it may have changed hands) and asks for the email form. Disabled rows are history and never change (trigger `wallet_identities_frozen_when_disabled`, which also stops the application role re-enabling one with its `UPDATE (disabled_at)`).
- *(0130)* **Signers** are the subject's active wallet only (`assertSubjectSigner`); attestations and gate decisions signed before a replace keep their recorded signer and stay valid history.
- *(0130)* **Governance (D9).** `designate_governance_wallet`, `POST /api/v1/auth/wallets/governance` and `subjects.governance_wallet_id` are removed; weight is read from the active wallet (`GOVERNANCE_WALLET_REQUIRED` without one). `governance_votes.weight_wallet_address` records the weight wallet, unique per proposal; a trigger pins it and the weight, so a re-vote after a replace changes only the choice, and a new holder of the old wallet gets `GOVERNANCE_WALLET_ALREADY_VOTED` (409).
- *(0130)* **Admins disable, never bind** — unchanged. `replaced` and `consolidated_single_wallet` are system reasons a person or admin cannot choose (`WALLET_REASON_INVALID` in `disable_own_wallet`; the request schema allows only the four person reasons), and a trigger refuses either on any insert not made by the table owner, so the application role's direct insert (the admin disable) cannot forge them.
- *(0130)* **Snapshot weight pinned** by the trigger on every snapshot proposal, also for a vote with no recorded weight wallet (votes from before `0130`).

- **SIWE login routes were not deleted in WP5; WP7 deleted them (`0125`, see "WP7 as built").** The web app, the E2E `connectAs` helper and the Chain E2E signed in with SIWE until WP6/WP7 replaced them. WP5 made the legacy path harmless meanwhile: with `LEGACY_WALLET_LOGIN` off (the production default) every SIWE route answers 404 `LEGACY_WALLET_LOGIN_DISABLED`, and legacy sign-in resolves only operator-bound wallets (`bound_via = 'operator'`: bootstrap, seed and pre-WP5 admin binds). A key the person bound by proof signs; it never signs in — otherwise a TOTP session could bind a key and reach `aal3` through the legacy route.
- **Binding** (`POST /api/v1/auth/wallets/binding-challenges`, then `POST /api/v1/auth/wallets`): an EIP-712 `WalletBinding` over purpose, tenant, subject, address, chain, nonce, issued/expires; domain "MPC Wallet Binding" v1 with the deployment chain and a fixed salt. One live challenge per session, 5 minutes, single use. Needs an account session at the strongest factor held (aal3 once a passkey exists, else aal2), never recovery-limited, never legacy. Any already-bound address answers one generic `WALLET_UNAVAILABLE` (409). EOA signatures only; no EIP-1271 path exists.

Disabling a proof-bound wallet never changes assurance; disabling an operator-bound one still recomputes from the active operator wallets (which can override a level set through the new route — the fail-safe direction).

The application role lost INSERT/UPDATE on `core.wallet_identities` (it keeps `UPDATE (disabled_at, version)` for the admin disable) and on `subjects.governance_wallet_id` (the column is gone since `0130`). - **Cookie session (BFF) in the web proxy** (`apps/web/src/proxy.ts`, `apps/web/src/lib/bff.ts`). The API stays bearer-only and reads no cookie (the proxy strips the `cookie` header). The browser's token lives in `__Host-mpc_session` (HttpOnly, Secure, `SameSite=Strict`, `Path=/`, no `Domain`, max-age bounded by the API's expiry and 8 h); plain-http development uses the unprefixed, non-Secure `mpc_session`, and production reads only the prefixed name, so the unprefixed one cannot be planted there. - **SameSite=Strict, not Lax.** Every request that needs the cookie is a same-origin `fetch`; the provider redirect lands on a page, which then calls the API itself. Nothing depends on Lax.
- **CSRF.** A non-GET/HEAD/OPTIONS request is refused (403 `CROSS_SITE_REQUEST_REFUSED`) unless `Sec-Fetch-Site` is `same-origin`; without that header, `Origin` must equal `WEB_ORIGIN` (else the request's own origin); with neither, it is refused when it would ride on the cookie, and the sign-in routes are checked that way whatever they carry (login CSRF). ## 8. Acceptance criteria

1. An uninvited email cannot obtain a session; the response does not reveal whether it is invited.
2. Invitation → code → second factor → "access pending" works end to end; no private data is visible without a role binding.
3. A first-factor-only session cannot read restricted data or perform any action except MFA and logout.
4. Roles requiring a passkey are not effective in a TOTP session; step-up to a passkey makes them effective.
5. Google and Microsoft sign-in work only for linked `(iss, sub)` / `(tid, oid)`; a matching email alone never signs in.
6. Recovery, email change, suspension and authenticator removal revoke every session of the subject; signed history is unchanged.
7. No route accepts a SIWE login; scan-worker and CRE work with service tokens, and a service token cannot reach a person-only route.
8. Attestation and gate-decision signatures are accepted only from the right subject's active wallet; an account holds one at a time and replacing it is atomic (D11).
9. Admins cannot attach an email, identity, authenticator or wallet to another subject.
10. The session token is not readable from page script; cross-origin mutations are refused.
11. Full journey (account → workspace → evidence → signed review → decision → disclosure approval → publication → anchor → public proof) passes in CI with the new login.
12. Threat model, acceptance map, `.env.example`, deployment and plan text are updated.

Status after WP7 (local evidence, 2026-11-02; per-criterion tests in [the acceptance map](acceptance-code-map.md) AUTH-01–12): 1–5 and 7–10 are met in the API and the web, with browser E2E for 2, 4, 5 and 10. 6 is met: suspension (0127) is two-person and revokes sessions, factors and linked identities, with reinstatement under the recovery separation. 11 passes locally — `golden-path.spec.ts`, `evidence-ledger.spec.ts` and `anchor-chain.spec.ts` on account login against a local anvil with `RegistryAnchorV1` and the anchor worker — and is not claimed until CI runs it. 12 is done for the threat model, the acceptance map, `.env.example`, the deployment doc and this plan.
